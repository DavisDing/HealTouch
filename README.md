## 1. 引言

### 1.1 项目背景

HealTouch 是一款面向推拿馆的内部管理软件，帮助推拿馆实现患者档案、治疗项目、治疗登记、收费、预存管理等核心业务的数字化管理，提升运营效率和服务质量。

### 1.2 项目目标

- 实现治疗项目的灵活管理（增删改查、分类管理）
- 建立完整的患者电子档案系统，支持小儿患者
- 实现治疗登记与账单管理，**不允许欠费**
- 提供预存费用管理，所有余额变动可追溯
- 支持多角色权限控制，确保操作安全

### 1.3 设计原则

- **治疗后补录**：不涉及预约、待治疗提醒，治疗完成后由前台或治疗师补录。
- **无在线支付**：软件仅记录缴费，不关联任何支付渠道，所有支付方式由人工确认。
- **不允许欠费**：收费时必须全额收齐，系统不提供部分支付保存功能；未完成支付的临时账单不得长期保留。
- **财务可追溯**：所有账单、预存流水、退款操作均有记录。
- **权限分离**：系统管理功能仅管理员可操作，治疗师不能收费。

### 1.4 术语定义

| 术语     | 说明                                                     |
| -------- | -------------------------------------------------------- |
| 患者     | 接受治疗服务的客户，分成人/小儿                          |
| 治疗师   | 执行推拿、面针等治疗操作的人员，来源于系统用户           |
| 治疗项目 | 推拿馆提供的服务项目，如小儿推拿、成人推拿、面针等       |
| 账单     | 一次治疗或多次治疗产生的费用记录，必须全额收款           |
| 预存     | 患者预先存入的金额，可用于支付账单                       |
| 系统管理 | 包含用户管理、权限管理、治疗项目管理的模块，仅管理员可见 |

## 2. 系统概述

### 2.1 系统定位

HealTouch 是推拿馆内部使用的管理软件，覆盖患者档案、治疗登记、收费、预存、项目管理、用户权限等全部业务环节。系统不涉及在线支付、预约排班、小票打印。

### 2.2 系统导航结构

```
HealTouch 推拿馆管理系统
├── 首页（工作台）
│   ├── 创建档案
│   ├── 治疗登记
│   ├── 账单管理
│   └── 预存管理
├── 患者管理
│   ├── 档案查询
│   └── 档案详情
├── 治疗登记
├── 账单管理
├── 预存管理
├── 数据统计（仅管理员/财务可见）
└── 系统管理（仅管理员可见）
    ├── 用户管理
    ├── 权限管理
    └── 治疗项目管理
        ├── 项目分类管理
        └── 治疗项目管理
```

- 首页提供业务快捷入口，不包含系统管理入口。
- 系统管理菜单及子菜单仅对**系统管理员**角色显示。
- 非管理员用户登录后看不到系统管理入口，直接访问URL也会被权限拦截。

- 所有退款操作（账单退款、预存余额退款）需管理员或具备退款权限的角色执行，并记录操作日志。

#### 4.2.2 档案操作

- **创建档案**：首页点击“创建档案”，选择患者类型，填写信息。相同证件类型和证件号码已存在时，系统提示已有档案并跳转至详情，禁止重复建档；姓名、出生日期、联系电话或监护人电话相同的记录需提示疑似重复，由操作者确认后方可建档。
- **查询档案**：支持按姓名、身份证号、手机号模糊搜索。
- **档案详情**：展示基本信息、历史治疗记录、历史账单、预存余额。
- **敏感信息修改**：姓名、证件号码等关键字段修改需记录日志（原值、新值、修改人、时间），且仅管理员或前台有权限。

**小儿患者特殊规则**：

- 患者类型为“小儿”时，监护人姓名、关系、电话为必填。
- 证件类型可选“户口本”或“出生证明”；填写证件号码后，仍按“证件类型+证件号码”唯一校验。

### 4.3 治疗登记与账单管理

#### 4.3.1 治疗登记

**入口**：首页“治疗登记”按钮。

**登记字段**：

- 患者（通过搜索选择，自动带入患者信息）
- 治疗日期（默认当天，可修改）
- 治疗项目明细（**支持多行，即同一账单多项目**）：
  - 项目（从启用项目中选择）
  - 单价（自动带入，**不可修改**，保证价格一致）
  - 数量/次数（默认1，可修改）
  - 小计 = 单价 × 数量
- 治疗师（从用户管理中选择角色为“治疗师”的在职用户）
- 治疗过程备注（可选）

**操作流程**：

```
点击“治疗登记” → 选择患者 → 添加治疗项目（可多行） 
→ 选择治疗师 → 填写治疗备注 → 点击“保存并收费”
→ 系统生成账单草稿（状态：待收费）
→ 进入收费界面
```

**待收费控制**：待收费仅是当前结算会话的临时状态，不代表可挂账。保存后必须立即进入收费界面；支付成功则转为“已支付”，操作者主动取消、支付失败或连续 30 分钟未完成支付则自动作废。作废账单不计入收入、应收、治疗统计，须记录作废原因和操作者。需重新收费时，重新发起治疗登记。

#### 4.3.2 收费规则（不允许欠费）

- 账单应收总额 = Σ(项目小计)，支持折扣调整（折扣需管理员权限，前台不可修改折扣）。折扣须记录折扣类型、折扣前金额、折扣额、折后应收、原因、授权管理员及授权时间；管理员可直接设置，前台只能提交折扣申请，未经授权不得收费。
- **实收总额必须等于应收总额，不允许部分支付或欠费。**
- 收费界面中，支付方式支持**多行拆分**：
  - 预存扣款
  - 现金
  - 微信
  - 支付宝
  - 银行卡
  - 其他
- 若选择“预存扣款”，系统实时校验患者预存余额是否足够覆盖该行金额；若不足，则阻止保存，并提示余额不足（可引导先充值或改用其他支付方式）。
- 所有支付方式金额之和必须等于实收总额，否则无法保存。
- 收费成功后：
  - 账单状态从“待收费”变为“已支付”。
  - 若含预存扣款，自动生成预存消费流水，扣减余额。
  - 生成治疗记录（状态：已完成）。

**账单状态定义**：

| 状态     | 说明                                                         |
| -------- | ------------------------------------------------------------ |
| 待收费   | 治疗已登记，尚未完成收费（中间态，系统强制要求进入收费界面完成） |
| 已支付   | 全额收款完成，账单有效                                       |
| 部分退款 | 已支付后发生部分退款                                         |
| 已退款   | 已支付后发生全额退款                                         |
| 已作废   | 待收费会话取消、支付失败或超时，未产生任何收款               |

> **注意**：不存在“部分支付”状态，因为收费时必须一次收齐。

#### 4.3.3 账单管理

- **查询**：按患者姓名、身份证号、治疗日期范围、账单状态查询。
- **查看详情**：展示账单明细、支付拆分、治疗记录。
- **修改**：仅“待收费”状态的账单可修改（未收费前），修改后需重新进行收费流程；已支付账单及关联治疗记录不得直接修改。
- **退款**：对“已支付”或“部分退款”账单可申请退款（需管理员/财务权限），退款流程见 4.5。
- **治疗记录更正**：已支付记录如存在日期、治疗师、项目、数量或备注错误，须发起更正单。更正单记录原值、新值、原因、申请人、审批人及时间；涉及金额或项目数量变化时，先完成对应退款或补收后才可生效。已完成服务不可物理删除。

### 4.4 预存管理

#### 4.4.1 功能概述

患者可预存费用，治疗收费时可直接从预存余额扣款。所有预存变动均生成流水记录，余额不可为负数。

#### 4.4.2 预存操作

- **充值**：前台权限即可。选择患者，输入充值金额，选择支付方式（现金/微信/支付宝/银行卡等），确认收款，余额增加，生成充值流水。
- **消费**：在账单收费时自动扣减，无需单独操作。生成消费流水，关联账单编号。
- **余额退款**：**仅管理员或财务权限**。进入预存管理 → 选择患者 → 点击“余额退款” → 输入退款金额 → 系统校验余额是否充足 → 选择退款方式（现金退回/原路退回等） → 确认后余额扣减，生成退款流水，记录操作人、时间、备注。

#### 4.4.3 预存流水字段

- 流水编号（系统生成，唯一）
- 患者ID/姓名
- 变动类型（充值/消费/账单退款退回/余额退款）
- 变动金额（正负数）
- 变动前余额
- 变动后余额
- 关联账单编号（消费或账单退款时）
- 支付方式（充值、消费退款或余额退款时）
- 操作人（当前用户）
- 操作时间
- 备注

#### 4.4.4 预存余额保护

- 数据库约束：余额字段 `balance >= 0`。
- 所有扣款操作在事务内执行，防止并发导致负余额。
- 余额退款需管理员或财务权限，并记录日志。

### 4.5 账单退款流程

**适用对象**：已支付或部分退款的账单。退款单与账单分离管理，一个账单可有多张退款单，但同一账单同一时刻仅允许一张“待审批”退款单。

**操作流程**：

```
账单管理 → 选择“已支付”或“部分退款”账单 → 申请退款
→ 选择退款明细（整单或部分项目/金额）并填写原因
→ 管理员/财务审批 → 具备执行权限的人员执行退款
→ 系统按原支付明细分摊退款：预存支付部分最多退回原预存实付额，剩余金额按原非预存支付渠道比例退回
→ 更新账单状态（部分退款/已退款）→ 生成退款记录
```

**退款规则**：

- 退款金额不得超过该账单实收总额减去已退款金额。
- 退款明细不得超过对应项目的已收未退金额；整单退款须覆盖全部未退款项目。
- 预存退款金额不得超过该账单原预存支付金额减去已退回预存金额；退回预存时生成关联退款单和账单的预存流水。
- 退款单状态为草稿、待审批、已驳回、已执行、已撤销。申请人不得审批自己的退款单；审批人与执行人可由同一人担任仅限系统管理员，财务/主管审批的退款必须由另一名具备执行权限的人员执行。
- 已执行退款不得修改或撤销；如发生误退，须以独立的补收账单处理。退款单需记录申请人、审批人、执行人、时间、原支付明细、退款方式、原因和备注。

### 4.6 系统管理（仅管理员）

#### 4.6.1 用户管理

**功能概述**：管理员维护所有系统使用者账号，分配角色，控制账号状态。

**用户字段**：

- 用户ID（系统生成）
- 姓名（用于治疗师选择）
- 登录账号（唯一）
- 登录密码（加密存储）
- 角色（可多选，如某用户既是前台又是治疗师）
- 手机号
- 状态（在职/停用）
- 创建时间、最后登录时间

**操作流程**：

```
管理员进入“系统管理” → “用户管理” → 新增用户 → 填写信息 → 分配角色 → 保存
→ 系统校验账号唯一 → 用户可用
→ 停用用户后，该用户不可登录，且不可被选为治疗师
```

**治疗师选择来源**：治疗登记界面中的“治疗师”下拉框，数据源为**用户管理中角色包含“治疗师”且状态为“在职”的用户**。若用户离职，管理员将其状态改为“停用”，该用户将不再出现在治疗师选择列表中，但历史治疗记录仍保留其姓名快照。

#### 4.6.2 权限管理

**功能概述**：管理员配置各角色的权限点，控制菜单和按钮的可见性。

**默认角色**：系统管理员、前台、治疗师、财务/主管，可扩展自定义角色。

**权限粒度**：模块级 + 操作级（查看、新增、修改、删除、审核等）。

**操作流程**：

```
管理员进入“系统管理” → “权限管理” → 选择角色 → 勾选/取消权限 → 保存
→ 权限即时生效
```

**权限点示例**（见权限矩阵）。

**角色合并与边界**：用户拥有多个角色时，业务权限按并集计算；系统管理员是内置不可配置角色，始终拥有系统管理权限。自定义角色不得授予用户管理、权限管理或系统管理入口权限；退款、统计等业务权限可由管理员按操作级配置。停用用户立即失效，正在进行的会话在下次请求时强制退出。

#### 4.6.3 治疗项目管理

**功能概述**：管理员维护治疗项目的分类和具体项目，其他角色仅可在治疗登记时选择启用项目。

**分类管理**：

- 分类层级：支持两级分类（大类 → 小类）。
- 默认大类：小儿推拿、成人推拿、面针、其他（可自定义）。
- 分类字段：分类名称、分类编码、排序、状态（启用/停用）。
- 权限：仅管理员可新增、修改、删除分类。
  - 删除分类前需检查其下是否有项目或历史账单关联；若有，则禁止删除，只能停用。

**项目管理**：

- 项目字段：
  - 项目名称（必填）
  - 项目编码（唯一，可选）
  - 所属分类（必选，关联分类表）
  - 标准价格（必填，数字）
  - 治疗时长（分钟，可选）
  - 项目描述（可选）
  - 适用人群（可选，如成人/儿童）
  - 注意事项（可选）
  - 状态（启用/停用）
- 权限：仅管理员可新增、修改、删除项目；其他角色仅可查看。
- 删除保护：若项目已被历史账单引用，禁止物理删除，只能停用。
- 价格快照：账单明细中冗余存储项目名称、单价，项目后续调价不影响历史账单。

### 4.7 数据统计与操作日志

#### 4.7.1 数据统计（管理员/财务可见）

- 日/月/年收入汇总：按支付成功时间统计已支付账单的实收；退款按执行时间以负数冲减，展示收入、退款和净收入。
- 支付方式汇总：按现金、微信、支付宝、银行卡、其他及预存扣款分别统计；预存充值单列为资金流入和预存负债变化，不计入服务收入，避免与账单消费重复计算。
- 项目销售排行：按已支付且未退款的项目数量和净额统计；部分退款按退款项目或退款金额扣减。
- 治疗师工作量统计：按已支付且未全额退款的治疗记录统计；已作废账单不计入。
- 预存余额总览与变动明细
- 退款记录统计

**统计口径**：收入均以支付成功和退款执行的自然日为准；页面须明确展示所选日期范围、统计口径及是否含退款。治疗日期仅用于治疗服务分析，不替代收入归集日期。

#### 4.7.2 操作日志

记录关键操作，包括但不限于：

- 患者档案敏感信息修改
- 项目管理（分类/项目）增删改
- 账单退款
- 预存余额退款
- 用户角色/权限修改

日志字段：操作时间、操作人、操作类型、操作对象、变更前后内容（可选）、IP地址。

## 5. 核心业务流程

### 5.1 患者建档流程

```
首页“创建档案” → 选择患者类型 → 填写基本信息（小儿必填监护人）
→ 选择证件类型并填号 → 证件类型+证件号码查重
→ 保存 → 生成患者ID → 完成
```

### 5.2 治疗登记与收费流程（不允许欠费）

```
首页“治疗登记” → 搜索选择患者 → 添加治疗项目（支持多行）
→ 选择治疗师 → 填写备注 → 点击“保存并收费”
→ 系统生成临时账单（待收费） → 进入收费界面
→ 确认应收总额 → 拆分支付方式（预存+现金等）
→ 若含预存，校验余额 → 实收总额=应收总额 → 确认收款
→ 账单状态变为“已支付” → 预存扣款生成流水 → 治疗记录完成
（取消、失败或超时 30 分钟未付款 → 账单作废，不产生应收）
```

### 5.3 预存管理流程

```
充值：预存管理 → 选择患者 → 充值 → 输入金额 → 选择支付方式 → 确认收款 → 余额增加，生成流水

消费：在账单收费中自动完成，无需单独操作

余额退款：预存管理 → 选择患者 → 余额退款 → 输入金额 → 校验余额 → 选择退款方式 → 确认 → 余额扣减，生成流水
```

### 5.4 账单退款流程

```
账单管理 → 选择“已支付”或“部分退款”账单 → 申请退款
→ 选择退款明细（整单或部分项目/金额）
→ 管理员/财务审批 → 授权人员执行
→ 系统按原支付明细分摊退款：预存最多退回原预存实付额，余额按原非预存渠道比例退回
→ 更新账单状态（部分退款/已退款）→ 生成退款记录
```

### 5.5 项目管理流程

```
管理员进入系统管理 → 治疗项目管理 → 维护分类（新增/修改/停用）
→ 维护项目（新增/修改/停用，关联分类，设置价格）
→ 其他角色仅可查看，治疗登记时从启用项目中选择
```

## 8. 数据安全与审计

### 8.1 账户与访问安全

- 登录密码使用不可逆强哈希存储，不记录明文密码；首次登录和管理员重置后必须修改密码。
- 密码至少 8 位，包含字母、数字和特殊字符；连续 5 次登录失败锁定账号 15 分钟，并记录安全日志。
- 登录会话空闲 30 分钟自动失效；账号停用、角色变更或密码重置后，原会话应立即失效。
- 所有接口均须在服务端校验权限，菜单隐藏不能作为权限控制依据。

### 8.2 患者数据保护

- 身份证号、联系电话、地址、过敏史和既往病史属于敏感信息。非必要页面应脱敏展示，导出功能仅管理员可用并记录导出范围、原因和操作人。
- 患者档案、治疗记录、账单、预存和日志的数据保留期限由门店管理员配置，任何到期清理须审批并生成不可修改的清理记录。

### 8.3 数据备份、导入与还原

**备份范围与存放**：完整备份包含患者档案、治疗记录、账单、支付明细、预存流水、退款单、用户与角色配置、治疗项目及操作日志；不包含当前登录会话和明文密码。系统每天在设定时间自动生成完整备份，也支持管理员手动备份。备份完成后自动保存到软件数据目录下的 `backups` 指定目录；管理员可在系统设置中修改该目录，修改前系统须校验目录可写且剩余空间充足。

- 备份文件使用统一格式（如 `.healtouch-backup`），文件名包含门店标识、生成日期时间与备份编号，例如 `HealTouch_Store001_20260817_230000_BK0001.healtouch-backup`。
- 每个备份包包含版本号、生成时间、数据清单、记录数量和校验值。生成后系统自动校验文件完整性；校验失败时标记备份失败、保留错误信息并提示管理员。
- 默认保留最近 30 个自然日的自动备份，手动备份不自动删除；管理员可调整自动备份保留天数，但不得少于 30 天。删除备份仅系统管理员可操作，须二次确认并记录日志。
- 备份目录不可用、空间不足或自动备份失败时，系统应在首页和管理员通知中持续提示，直至备份成功；不得静默失败。
- 完整备份文件须加密保存。导出或恢复时由管理员输入备份口令；口令不写入日志或备份文件明文。

**导出功能**：管理员可按权限导出患者、治疗记录、账单、预存流水、退款记录、统计报表和操作日志。导出文件为只读数据文件（CSV/XLSX/PDF 等），包含导出范围、生成时间和操作者；业务导出仅供查询、审计或迁移，不能直接用于系统还原。涉及敏感字段的导出默认脱敏，导出完整敏感信息须填写原因并写入日志。

**导入与还原功能**：

- “数据导入”用于首次迁移或补充基础资料，仅允许导入经系统模板校验的患者、项目、用户等非财务基础数据；账单、支付、预存、退款和操作日志不允许通过普通导入写入，避免破坏资金流水。
- “完整还原”仅接受系统生成的 `.healtouch-backup` 备份包，且仅系统管理员可执行。系统先校验备份口令、文件校验值、版本兼容性和数据完整性，再展示备份时间、数据摘要及将被替换的数据范围。
- 还原前系统自动对当前全部数据生成一份紧急备份，并要求管理员二次确认；还原过程锁定其他用户写入操作。还原成功后记录还原前后备份编号、操作人、时间和结果，并强制所有用户重新登录。
- 还原失败时，系统不得提交部分数据；须回滚到还原前状态，并保留失败原因与紧急备份，供管理员重新执行或联系技术支持。
- 每季度至少执行一次“在测试环境使用备份还原”的恢复演练，并记录备份编号、恢复耗时、校验结果和问题处理情况。

### 8.4 审计完整性

- 账单支付、充值、预存扣款、退款、作废、更正和折扣授权均须写入操作日志与业务流水；日志只允许查询，不允许普通业务操作修改或删除。
- 所有金额写入以最小货币单位存储和计算，金额必须大于 0，防止浮点误差和零金额交易。
- 预存扣款、账单状态变更及对应流水必须在同一数据库事务内提交；对患者余额记录加锁，避免并发重复扣款。

## 10. Java 技术方案与部署

### 10.1 确定技术栈

| 技术项           | 确定方案                     | 说明                                          |
| ---------------- | ---------------------------- | --------------------------------------------- |
| 开发语言         | Java 8                       | 满足 Windows 7 SP1 至 Windows 11 的兼容目标。 |

| 数据库迁移       | Flyway                       | 以版本化脚本管理数据库结构变更。              |
| Windows 启动程序 | Launch4j                     | 生成 Windows `.exe` 启动程序。                |
| 安装打包         | Inno Setup                   | 打包应用、依赖和对应位数的 Java 运行时。      |

### 10.2 操作系统与发布要求

| 项目       | 要求                                                         |
| ---------- | ------------------------------------------------------------ |
| 支持系统   | Windows 7 SP1、Windows 8.1、Windows 10、Windows 11           |
| 不支持系统 | Windows XP、Windows Vista、未安装 SP1 的 Windows 7           |
| 32 位交付  | `HealTouch-x86-Setup.exe`                                    |

### 10.3 单机架构与维护边界

```text
JavaFX 8 表现层
    ↓
业务服务层（患者、治疗、收费、预存、退款、权限）
    ↓
DAO 数据访问层（JDBC + HikariCP）
    ↓
SQLite 本地数据库
```

- Maven 依赖版本必须锁定在兼容 Java 8 和 Windows 7 的版本。
- 金额使用整数形式保存最小货币单位；收费、充值、扣款和退款在同一个事务中完成。
- 数据库结构通过 Flyway 脚本升级，禁止手工修改生产数据库结构。
- SQLite 数据库文件不得放在共享网络盘供多台电脑同时打开；本期为单机使用。
- 未来需要多台电脑同时使用时，保留 JavaFX 客户端，增加 Spring Boot 服务端，并迁移至 PostgreSQL 或 SQL Server；该升级不属于本期范围。

### 10.4 发布验证

每次发布至少在 Windows 7 SP1、Windows 10 和 Windows 11 上分别验证 x86/x64 安装包，检查安装、首次启动、数据库初始化、升级、备份恢复、卸载后数据保留及程序无 Java 环境时的启动行为。

### 10.5 GitHub Actions 自动构建与打包

项目使用 GitHub Actions 自动完成构建、测试和 Windows 安装包生成，正式发布不依赖开发人员本地手工打包。

**工作流要求**：

- 工作流文件统一放在 `.github/workflows/` 目录。
- Pull Request 时执行 Java 编译、依赖检查、数据库迁移检查和自动化测试；每次推送到主分支都会在上述检查通过后，自动生成 x86/x64 Windows 安装包并保存为 Actions Artifact。
- 创建版本标签（格式如 `v1.0.0`）时，执行同一套正式构建，生成 x86 与 x64 两个 Windows 安装包，并自动创建 GitHub Release。
- Windows 构建任务使用 `windows-latest` runner；Java 8、Maven、Launch4j、Inno Setup 的版本必须固定。
- 打包前执行清理构建，禁止将本地数据库、用户数据、日志和备份文件打入安装包。

**正式构建产物**：

```text
HealTouch-<version>-x86-Setup.exe
HealTouch-<version>-x64-Setup.exe
SHA256SUMS.txt
```

构建产物作为 GitHub Actions Artifact 保存；正式版本同时创建 GitHub Release，并上传两个安装包及校验文件。版本号来自 Git 标签（去掉 `v` 前缀），并写入安装包文件名；主分支的非正式构建使用 `0.0.0.<GitHub run number>` 作为可追溯版本号。

**首次启用前的仓库配置**：在 GitHub 仓库的 **Settings → Secrets and variables → Actions** 中创建下列 Repository secrets。运行时压缩包必须是受控、可长期访问的 Windows Java 8（含 JavaFX）运行时；工作流会校验 SHA-256，校验失败即停止发布。

| Secret | 内容 |
| --- | --- |
| `HEALTOUCH_RUNTIME_X86_URL` | x86 JavaFX 8 Runtime ZIP 的 HTTPS 下载地址 |
| `HEALTOUCH_RUNTIME_X86_SHA256` | 该 x86 ZIP 的 64 位十六进制 SHA-256 值 |
| `HEALTOUCH_RUNTIME_X64_URL` | x64 JavaFX 8 Runtime ZIP 的 HTTPS 下载地址 |
| `HEALTOUCH_RUNTIME_X64_SHA256` | 该 x64 ZIP 的 64 位十六进制 SHA-256 值 |

> 不要在仓库中提交运行时 ZIP、下载凭据或签名证书。推送到 `main` 后可在 **Actions** 页面下载构建产物；推送例如 `v1.0.0` 的标签后会额外创建正式 Release。

**质量门禁与安全要求**：

- 任一编译、测试、数据库迁移检查、打包或完整性校验失败，工作流必须失败，不得发布不完整安装包。
- 正式发布前生成两个安装包的 SHA-256 校验值。
- GitHub Actions 不保存患者数据、生产数据库、备份口令或其他敏感信息；签名证书等凭据只能保存在 GitHub Actions Secrets 中。
- 工作流保留构建日志和版本产物，发布权限仅限受保护的主分支或正式版本标签。

## 开发实现说明

本仓库现已提供 Java 8/JavaFX 8 单机实现骨架与核心业务代码：

- `src/main/resources/db/migration/`：Flyway 管理的 SQLite 数据库结构和默认角色/分类；金额统一使用分（`*_cents`）保存。
- `src/main/java/com/healtouch/service/`：患者、项目、治疗登记、全额收费、预存、退款审批/执行、认证和审计等事务服务。
- `src/main/java/com/healtouch/ui/`：JavaFX 登录、工作台、患者、治疗收费、账单、预存、用户和项目管理页面。
- `src/test/`：覆盖小儿监护人校验、全额收费和预存扣款的核心流程测试。
- `.github/workflows/build.yml`：PR 验证、每次推送 `main` 的 Windows x86/x64 安装包 Artifact，以及 `vX.Y.Z` 标签的 SHA-256 和 Release 发布流程。

### 本地运行

要求使用 **带 JavaFX 的 JDK 8**：

```bash
mvn clean test
mvn clean package
```

当前 Maven 配置生成可执行 fat jar；也可使用：

```bash
mvn clean package
java -jar target/healtouch-1.0.0-SNAPSHOT-shaded.jar
```

首次启动会在用户目录创建 `HealTouch/healtouch.db`，不会写入安装目录。默认账号为 `admin`，初始密码为 `Admin@123`，首次登录必须修改密码。

> 生产发布时，GitHub Actions 中的 `HEALTOUCH_RUNTIME_X86_URL`、`HEALTOUCH_RUNTIME_X64_URL` 及对应的 SHA-256 Secrets 必须配置为经审计、固定版本的 JavaFX 8 Runtime；其内容随对应安装包内置，不存储任何业务数据。
